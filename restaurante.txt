RESTAURANTE PRO
Especificación funcional, técnica y de seguridad de un sistema profesional de pedidos y gestión para
restaurantes
Objetivo del documento
Este documento define una propuesta completa para una aplicación profesional de restaurante. El sistema integra
pedidos mediante QR, menú digital, cocina, meseros, caja, administración, inventario, clientes, reportes,
notificaciones, usuarios y seguridad. La arquitectura está pensada para poder crecer desde un solo restaurante
hasta una plataforma multi-restaurante.
1. Visión general del sistema
La aplicación funcionará como un sistema centralizado. Los clientes pueden pedir desde su teléfono escaneando el
QR de una mesa; cocina recibe el pedido en tiempo real; el mesero controla las mesas y entrega los platos; caja
procesa el pago; y el administrador controla productos, inventario, usuarios y reportes.
Flujo principal
Cliente → QR de mesa → Menú → Carrito → Pedido → Cocina → Preparación → Listo → Mesero → Entrega
→ Caja → Pago → Reporte
2. Roles y permisos
Administrador: Control total del restaurante: productos, categorías, mesas, usuarios, inventario, clientes,
promociones, reportes, configuración y auditoría.
Mesero: Visualiza mesas, crea pedidos manualmente, consulta pedidos activos, recibe avisos de cocina y registra
solicitudes.
Cocina: Visualiza pedidos nuevos y cambia su estado: recibido, preparando y listo. No debe acceder a funciones
administrativas.
Cajero: Consulta pedidos pendientes, procesa cobros, registra métodos de pago, descuentos y comprobantes.
Cliente: Consulta el menú, agrega productos al carrito, realiza pedidos, observa el estado y consulta su historial
cuando exista una cuenta.
3. Aplicación del cliente
Acceso mediante QR: Cada mesa tendrá un QR único. Al escanearlo, el sistema identifica el restaurante y la mesa
sin que el cliente tenga que escribirla.
Menú digital: Categorías, fotografías, nombre, descripción, precio, ingredientes, extras, disponibilidad y
recomendaciones.
Carrito: Cantidad, extras, observaciones, subtotal, impuestos, descuentos y total.
Pedido: Confirmación antes de enviar, número de pedido y seguimiento del estado.
Historial: Opcionalmente, el cliente registrado puede consultar pedidos anteriores, favoritos y beneficios.
4. Sistema de mesas
Estados: Libre, ocupada, esperando pago, reservada y fuera de servicio.
Información: Número de mesa, capacidad, pedido activo, personas, hora de apertura y total acumulado.

Métodos: Efectivo, tarjeta, transferencia u otros configurados por el administrador.
Descuentos y propina: Aplicar únicamente según los permisos del usuario.
Cierre: Resumen de ventas por turno, efectivo esperado, pagos registrados y diferencias.
Comprobantes: Generar comprobante o recibo según la configuración y normativa aplicable.

Productos: Crear, editar, desactivar y eliminar productos.
Categorías: Organizar el menú por categorías.
Imágenes: Subir fotografías optimizadas.
Extras: Crear opciones como queso adicional, salsas, bebidas o tamaños.
Disponibilidad: Marcar productos como disponibles o agotados.
Precios: Controlar precio normal, promociones y posibles variantes.
9. Inventario
Ingredientes: Registrar materias primas y unidades de medida.
Stock: Cantidad actual, stock mínimo y alertas.
Movimientos: Entradas, salidas, ajustes y motivos.
Descuento automático: Una venta puede descontar ingredientes según una receta configurada.

Página 314. Seguridad de la aplicación
La seguridad debe diseñarse desde el inicio. No se debe confiar en que la aplicación móvil o web oculte funciones: el
servidor debe validar permisos en cada operación.
Autenticación: Contraseñas almacenadas con un algoritmo de hash seguro; nunca guardar contraseñas en texto
plano. Implementar recuperación de cuenta y sesiones con expiración.
Autorización: Aplicar RBAC (Role-Based Access Control). Un usuario de cocina no debe poder modificar precios ni
un cajero administrar usuarios.
HTTPS: Toda comunicación entre aplicación, API y servidor debe utilizar HTTPS/TLS.
Tokens y sesiones: Usar tokens de corta duración y mecanismos seguros de renovación. Revocar sesiones cuando
sea necesario.
Validación en servidor: Validar todos los datos recibidos: cantidades, precios, IDs, permisos, estados y totales. El
cliente nunca debe ser la fuente de verdad del precio final.
Protección contra inyección: Usar consultas parametrizadas/ORM y nunca concatenar directamente datos del
usuario en consultas SQL.
Control de acceso por restaurante: En modo multi-restaurante, cada consulta debe estar vinculada al
restaurant_id del usuario. Un restaurante jamás debe poder consultar datos de otro.
QR seguro: El QR no debe contener información sensible. Debe usar un identificador o token que pueda invalidarse
y renovarse.
Auditoría: Registrar acciones importantes: inicio de sesión, creación/edición de productos, cambios de precios,
anulaciones, descuentos, cobros y modificaciones de inventario.
Copias de seguridad: Programar respaldos de base de datos, comprobar que puedan restaurarse y limitar el
acceso a las copias.
Protección contra abuso: Aplicar rate limiting, límites de intentos de inicio de sesión y protección contra solicitudes
automatizadas.
Datos personales: Recopilar únicamente los datos necesarios, limitar accesos y establecer políticas de
conservación y eliminación.
Secretos: Claves API, contraseñas de base de datos y credenciales nunca deben estar dentro del código público de
la aplicación. Usar variables de entorno o un gestor de secretos.
Errores: No mostrar al usuario mensajes que revelen contraseñas, consultas SQL, rutas internas o detalles del
servidor.
15. Arquitectura técnica recomendada
Una arquitectura moderna puede dividirse en cuatro capas principales:
1) Aplicación móvil/web → 2) API/backend → 3) Base de datos → 4) Servicios externos (notificaciones,
almacenamiento de imágenes, pagos, etc.)
Frontend
Puede desarrollarse como aplicación móvil multiplataforma (por ejemplo, React Native/Expo) y, si se desea,
acompañarse de un panel web para administración, cocina y caja.
Backend
El backend centraliza autenticación, permisos, pedidos, productos, inventario, pagos, reportes y comunicación en
tiempo real.

Una base de datos relacional como PostgreSQL o MySQL es apropiada para usuarios, restaurantes, mesas,
productos, pedidos, detalles de pedidos, pagos e inventario.
Tiempo real
Para que cocina, meseros y clientes reciban cambios sin actualizar manualmente, se puede utilizar WebSockets, un
servicio realtime o una tecnología equivalente.

19. Modo multi-restaurante (opcional y avanzado)
Si el objetivo es convertirlo en un producto comercial, el sistema puede permitir que varias empresas usen la misma
plataforma. Cada restaurante tendría sus propios usuarios, mesas, productos, inventario, clientes y ventas. La
separación de datos debe estar aplicada en el backend y en la base de datos.
Ejemplo:
Restaurante A → usuarios + mesas + productos + ventas
Restaurante B → usuarios + mesas + productos + ventas
Restaurante C → usuarios + mesas + productos + ventas

21. Diseño y experiencia de usuario
La interfaz debe ser sencilla y rápida. Cocina necesita botones grandes y estados visibles; caja necesita acceso
rápido a cobros; el cliente debe poder realizar un pedido con pocos pasos. El diseño debe ser responsive y
adaptarse a teléfonos, tablets y computadoras.
Pantallas principales sugeridas
Splash → Login → Selección de rol → Dashboard → Mesas → Menú → Producto → Carrito → Pedido →
Cocina → Caja → Reportes → Configuración

23. Resultado esperado
Al finalizar, Restaurante Pro sería más que una aplicación para tomar pedidos: sería un sistema de gestión para
restaurantes que conecta al cliente, cocina, meseros, caja y administración mediante una plataforma centralizada.
Nota: las funciones de facturación electrónica, pagos, protección de datos y otros requisitos legales deben adaptarse a la
normativa vigente del país donde se implemente el sistema y a los proveedores utilizados.
